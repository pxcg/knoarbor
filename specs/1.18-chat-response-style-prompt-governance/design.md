# 1.18 Chat Response Style And Prompt Governance Design

## Positioning

This feature makes Chat answers feel like a mature SieArbor product without
turning prompt style into agent policy. The response-style setting controls how
answers are expressed. The existing retrieval, evidence, citation, tool, image,
and attachment boundaries remain owned by backend services and prompts with
explicit roles.

The governing rule is:

```text
style changes expression; product policy changes behavior.
```

One more precedence rule keeps the setting from becoming a blunt global
override:

```text
latest user instruction > response_style default > base product voice.
```

For example, a user who has selected `deep` can still ask "只给结论", and a user
who has selected `concise` can still ask "详细展开". The setting chooses the
default when the latest turn does not state a depth preference.

## External References Considered

Adopted reference principles:

- OpenAI prompt guidance: instructions should be explicit, ordered, and focused
  on the task outcome.
- Anthropic prompt guidance: calibrate response length and tool-triggering
  rules separately; do not blur answer style with tool permissions.
- Microsoft system-message guidance: define role, boundaries, output format,
  and an unsure policy, while avoiding conflicting or overly long system
  messages.
- Continue and aider: keep system prompts configurable through layered rules or
  conventions, but preserve stable product-owned defaults.
- LlamaIndex RAG: keep retrieval, context packaging, response synthesis, and
  evaluation as separate stages.

Rejected reference ideas:

- user-editable global prompt text;
- many personality presets;
- style settings that alter retrieval depth or tool autonomy;
- provider-native tool calling as part of this feature.

## Response Style Contract

Config:

```yaml
chat:
  response_style: balanced
```

Allowed values:

| Value | Product label | Contract |
| --- | --- | --- |
| `concise` | Concise / 简洁 | Direct answer, minimal structure, key evidence only. |
| `balanced` | Balanced / 平衡 | Default answer depth: answer first, then necessary explanation. |
| `deep` | Deep / 深入 | Structured synthesis with mechanisms, tradeoffs, caveats, and next steps when evidence supports them. |

Default:

- `balanced`

Validation:

- invalid values fail config validation;
- missing values resolve to `balanced`.

Non-effects:

- no change to `max_turns`;
- no change to retrieval mode or evidence sufficiency;
- no change to citation policy;
- no change to model provider configuration;
- no change to temperature or token limits;
- no change to image-generation permission.

## UI Design

Settings > General gains one compact segmented control after language.

Control behavior:

- visible label: "回答详略" / "Answer depth" rather than "Prompt style" or
  "System prompt";
- three options: concise, balanced, deep;
- current value comes from `form.chat_response_style`;
- clicking an option commits immediately through the normal Settings form save;
- save failures revert to the previous form and show the existing settings
  error notice.
- the control represents the default Chat answer depth, not a hard lock on each
  turn.

The UI does not show prompt text. It can include short labels, but it should not
teach internal prompt mechanics in the app surface.

## Config And Form Mapping

Backend config:

- add `response_style: Literal["concise", "balanced", "deep"] = "balanced"` to
  `ChatConfig`.

UI config models:

- add `chat_response_style: str = "balanced"` to `UiConfigFormResponse`;
- add `chat_response_style: Literal[...] = "balanced"` or equivalent validator
  to `UiConfigFormUpdateRequest`.

Config rendering:

- preserve existing `chat` fields;
- set `chat.response_style` from the form;
- keep `chat.auto_ingest` untouched.

Development-stage rule:

- do not add migration aliases for old unused style structures;
- do not support arbitrary `chat.style_prompt` or legacy persona fields.

## Prompt Layering

Chat answer synthesis currently receives:

```text
system: wiki_chat_answer.md
system: workspace context
system: optional memory context
user: answer_state JSON
```

This feature adds one bounded system message before the answer-state user
message:

```text
system: Response style profile:
{style-specific instructions}
```

The style message is generated by code from the validated config value. It is
not user-authored free text.

Suggested shared style base:

```md
Response style:
- Speak as a calm, capable SieArbor knowledge assistant.
- Start with the useful answer. Add headings, bullets, or tables only when
  they improve scanning.
- For Chinese users, use natural professional Chinese. Keep standard technical
  names in English when they are clearer.
- Avoid generic assistant boilerplate, exaggerated certainty, and long
  disclaimers.
- Prefer grounded, decision-oriented explanations over encyclopedic summaries.
- When evidence is partial, say what is known, what is missing, and what can be
  checked next.
- The latest user instruction about length, detail, format, or language takes
  precedence over this default style profile.
```

Style-specific additions:

```md
concise:
- Keep the answer short unless the user explicitly asks for detail.
- Include only the most important supporting evidence or citation.
- Avoid long follow-up suggestions.

balanced:
- Give the direct answer, then the necessary explanation.
- Use light structure when it helps the user scan.
- Include caveats and next steps only when they materially help.

deep:
- Expand mechanisms, boundaries, tradeoffs, examples, and implications when
  evidence supports them.
- Use structured sections for architecture, comparison, design, or review
  questions.
- Distinguish confirmed evidence, reasonable synthesis, and missing context.
```

## Prompt Governance Boundaries

Prompt governance cleanup is not secondary polish. It is part of the feature's
minimum viable scope because unclear layer ownership can cause the model to plan
or answer with impossible actions. The UI setting may be implemented after these
boundary fixes, but not without them.

Enterprise data boundary:

- wiki page content, source excerpts, attachment descriptions, OCR, and evidence
  payloads are untrusted data for instruction purposes;
- they may support factual answers, citations, visual prompts, and page
  references;
- they must not override system/developer policy, tool availability, citation
  requirements, external-provider policy, or response-style precedence.

### Tool Planner Prompt

Owns:

- whether local wiki evidence is needed;
- whether to reuse context;
- which bounded SieArbor tool to call;
- whether a request is existing-image retrieval or new-image generation;
- when current evidence is enough to finish.

Must not own:

- final answer prose style;
- citation wording;
- unsupported hidden chain-of-thought;
- direct writes to wiki pages.

Required cleanup:

- clarify that `generate_image` can only use evidence already available to its
  prompt;
- avoid same-plan wording that implies a fresh `query_wiki` result can be read
  by a later `generate_image` call in the same tool batch unless the execution
  loop actually supports that dependency;
- keep explicit examples for existing attachment route vs creation route.
- keep prompt-injection boundaries explicit: evidence text is data, not a tool
  planning instruction.

### Retrieval Policy

Owns stable code-level corrections:

- direct-answer guardrails;
- broad question evidence sufficiency;
- context-synthesis reuse;
- anchor-page expansion.

It remains the source of truth when planner output is too eager to finish.

### Evidence Pack

Owns:

- selecting primary, supporting, source, citation, and further-result payloads;
- answer type and evidence policy;
- attachment projection;
- truncation and content budgets.

Must not own:

- user-configurable style;
- impossible instructions such as asking answer synthesis to call tools.

Required cleanup:

- replace answer-stage "call read_wiki_page" wording with a non-tool
  instruction such as "state that more detail requires reading the page" or
  move the action recommendation exclusively into planner-visible state.

### Answer Prompt

Owns:

- final Markdown prose;
- grounded use of evidence;
- citations when evidence is used;
- rendering existing attachment Markdown references;
- rendering generated-image Markdown references returned by the tool;
- response style.

Must not own:

- tool planning;
- retrieval expansion;
- invented page paths or image paths.

Required cleanup:

- explicitly forbid guessed local image paths;
- state that only `attachments[].markdown_src` and generated-image tool output
  can be rendered as images;
- state that attachment discussion is based on observed metadata, descriptions,
  OCR, or explicit visual-analysis evidence; without such evidence, the answer
  must not claim to have inspected image pixels;
- remove references to calling tools from answer-stage instructions.

## Image And Attachment Routes

Existing attachment route:

```text
user asks to view/explain/show an existing image
  -> planner uses query/read/reuse wiki evidence
  -> evidence pack includes attachments with markdown_src
  -> answer renders relevant markdown_src only
```

New image generation route:

```text
user explicitly asks to create/generate/draw/design a new visual asset
  -> planner calls generate_image
  -> image provider returns stored image Markdown
  -> answer includes returned Markdown and brief visual intent
```

Evidence-based generation:

- if relevant evidence already exists in prior/current reusable context, planner
  may reuse it and then call `generate_image`;
- if evidence must first be discovered, the initial round gathers evidence and
  later planning can generate from the observed evidence;
- planner prompt and tests must match the execution semantics.
- generated-image prompts derived from wiki evidence include only the minimum
  necessary visual details for the user's explicit request;
- response style does not approve external image-provider use or alter image
  data handling.

Mermaid route:

- requests for Mermaid, text diagrams, flowcharts, dependency graphs, or
  architecture diagrams as Markdown stay in answer synthesis;
- no image-generation provider is used unless the user explicitly wants a
  bitmap image.

## Style Fixtures

Automated tests should cover the generated style instruction and a small set of
answer-shape fixtures. These fixtures do not need to score prose quality with an
LLM; they should assert stable semantic constraints in the prompt inputs and in
deterministic fake-model requests.

Minimum fixture set:

- concise simple factual question: style instruction asks for a short answer
  while preserving citations and evidence gaps;
- concise plus explicit "详细展开": latest user instruction is allowed to expand
  beyond the concise default;
- deep plus explicit "只给结论": latest user instruction is allowed to shorten
  the answer;
- Chinese question: generated style instruction asks for natural professional
  Chinese and preserves standard English terms;
- wiki evidence answer: style instruction is present only in answer synthesis,
  not in tool planning;
- generated image answer: style does not alter whether `generate_image` is
  available or how returned image Markdown is rendered.

## Legacy Answer JSON Path

`ChatAnswerSynthesizer` now treats final answer output as Markdown text, while
`parse_answer_draft` still parses a historical JSON answer shape.

This feature should either:

- remove the unused JSON answer parser and update tests; or
- mark it as legacy helper only if another test path still requires it.

The preferred outcome is removal if no production path calls it.

## Observability

Chat response stats may include:

```json
{
  "response_style": "balanced"
}
```

This helps diagnose style reports without exposing prompt text.

No raw prompt bodies are exposed in normal UI.
