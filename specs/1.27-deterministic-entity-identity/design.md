# 1.27 Deterministic Entity Identity Design

## Status

Accepted target design for public convergence. Implementation remains pending.

## Decision

Entity identity uses two separate objects:

```text
SourceEntityContribution
  contribution_key
  source_id / revision_id
  source_name
  aliases[]
  evidence[]
  -> deterministic resolver
CanonicalEntity
  entity_id
  canonical_name
```

`LinkedSourceKnowledge` retains both objects and maps every contribution key to
one canonical entity ID. Linking creates a new typed result; it does not mutate
the validated source knowledge supplied by 1.26.

## Contribution Ownership

Names, aliases, and evidence are source facts. They remain in the published
revision even when multiple contributions resolve to one canonical entity.
Canonical entities provide vault graph identity and display labels; they do not
replace source provenance.

The transactional publication boundary receives the complete contribution set
directly. It must not reconstruct contributions from display-oriented canonical
entity objects.

## Resolution Rules

Resolution order:

1. existing contribution identity for the same active source lineage;
2. exact normalized canonical name;
3. exact validated alias with one canonical target;
4. unambiguous explicit acronym;
5. create a new canonical entity ID.

Conflicting or multi-target aliases are unresolved. Fuzzy, embedding, topical,
or model-based matching does not merge identities during ingest.

## Identity Stability

Canonical entity ID is generated by deterministic code and remains stable when
the preferred display name changes. Registry rows are derived from active
source contributions selected by factual source heads. Rebuilding the registry
from those contributions produces the same mapping.

## Linked Knowledge Contract

The linker rewrites:

- source contribution keys to `canonical_entity_id` mappings;
- claim contribution references to `entity_ids`;
- relation subject/object contribution references to canonical endpoint IDs.

It preserves source display-name snapshots for readable projection. Names are
never used as the final graph reference.

## Diagnostics

Link diagnostics report created, reused, and unresolved identities plus the
deterministic rule used. They do not become knowledge facts or model context.

## Rejected Alternatives

- Clearing aliases after canonical resolution: loses source facts and breaks
  restart-stable alias linking.
- Name-only claim references: canonical rename or merge breaks graph closure.
- Model/embedding linking during ingest: introduces non-deterministic global
  mutation.
- Persisting only a materialized registry: loses reconstructability from facts.
