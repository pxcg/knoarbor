# 路线图

KnoArbor 已经走过最初的 1.x 到 2.0 长期兼容基线。当前方向是桌面端优先：继续把 Python/FastAPI core 作为执行引擎，同时让桌面应用成为用户使用 Chat、知识库运行、配置、报告、Wiki 浏览和安装发布的主要入口。

这份路线图是方向性规划。[能力地图](CAPABILITY_MAP.md) 记录能力状态，[ADR](../adr/README.md) 记录长期决策，多步骤实现工作放在 [`specs/`](../../specs/README.md)。

## 当前优先级

| 主题 | 方向 | 目标结果 |
| --- | --- | --- |
| 桌面应用 | Electron 是主要产品壳，web bundle 作为内嵌 UI 资产保留。 | 用户从一个桌面应用操作 KnoArbor，不再依赖源码构建网页流程。 |
| 知识库迁移 | 让 vault 数据、会话、附件、生成图片、报告和索引易于备份和跨机器迁移。 | 用户迁移桌面端 vault 时不会丢失会话证据或本地资产。 |
| Wiki 优先对话 | Chat 继续受限于 KnoArbor 工具、页面证据、引用、附件和默认生图参数。 | 回答可检查，并能回到维护后的 Wiki 页面和来源证据。 |
| 知识编译稳定性 | 在扩展大量新来源之前，先稳住标准化、文档预处理、分段、写入策略和报告。 | 富文档和长对话进入同一条可追溯 ingest 路径。 |
| 配置清晰度 | 随着桌面端基线稳定，减少重叠的配置发现、legacy 迁移和重复兜底路径。 | 桌面端和服务配置在升级中保持可预测。 |
| 打包与发布 | 使用自动化 macOS/Windows 构建、发布说明和干净仓库门禁。 | 发布版本包含用户真正安装的桌面应用。 |
| 文档卫生 | 公开文档聚焦当前产品表面；一次性治理记录单独归档。 | 用户和维护者能判断每份文档负责哪个决策。 |

## 后续方向

以下能力仍有价值，但不应抢占桌面端优先基线：

- index contract 后的可选向量检索；
- 更丰富的外部 source connector；
- 协作或云同步流程；
- 托管多用户服务；
- 更多文档预处理 provider；
- 页面关系之外的高级图谱分析。

## 非目标

KnoArbor 应保持为本地优先的知识引擎，并能被其他工具调用。它不应变成：

- 通用聊天助手；
- 隐藏的浏览器或文件系统自动化 agent；
- 必选云服务；
- 内置大模型分发；
- 缺少可追溯报告却自动改写用户 vault 数据的系统。

## 指导原则

- 优先稳定契约，再扩展功能广度。
- source connector 保持窄而可测试。
- 语义 agent 只处理需要语言理解的决策。
- 确定性校验不要交给模型。
- 不用宽泛兜底隐藏失败，而是输出可操作错误和报告。
- vault 是用户数据，测试和初始化都不能覆盖它。
- 每个生成或维护后的页面都必须能追溯到来源证据。
