# 路线图：1.0.0 到 2.0.0

KnoArbor 1.0.0 是第一个公开的本地优先版本，已经具备知识编译、校验维护、知识查询、本地控制台、API、CLI 和 Skill 集成的基础能力。

从 1.0.0 到 2.0.0 的核心目标是：

> 从“可用的本地 AI Wiki 引擎”演进为“稳定、可扩展、适合外部用户长期使用的知识系统”。

这份路线图是方向性规划，不是严格承诺。后续小版本可能根据真实实现和用户反馈调整顺序。

## 版本主题

| 版本 | 主题 | 目标结果 |
| --- | --- | --- |
| 1.1.x | 安装与启动体验 | 新用户可以低摩擦地安装、配置、启动，并生成第一批 Wiki 页面。 |
| 1.2.x | 配置生命周期 | 配置文件、知识库路径、模型供应商和迁移流程更安全、更清晰。 |
| 1.3.x | 资料来源生态 | 新输入来源可以作为清晰的 connector 接入，而不污染 ingest 主流程。 |
| 1.4.x | 机器索引层 | 在向量检索之前，先用轻量机器索引提升本地检索稳定性。 |
| 1.5.x | 知识治理 | lint 从结构修复扩展为质量、重复、溯源、时效性的持续治理。 |
| 1.6.x | 控制台产品化 | 本地控制台从开发控制台走向成熟的产品界面。 |
| 1.7.x | CLI、API、Skill 闭环 | 终端、HTTP 和宿主 AI 工具都能稳定使用同一套核心能力。 |
| 2.0.0 | 长期兼容基线 | 配置、API、connector、vault 和报告 schema 进入长期兼容阶段。 |

## 1.1.x：安装与启动体验

目标：让新用户的前十分钟足够顺畅。

重点：

- 继续完善 npm launcher，让 Node 优先用户更容易发现并启动 Python runtime。
- 保留 `uv`/Python 安装作为稳定参考路径。
- 强化 `knoar init`、`knoar doctor`、`knoar serve` 的下一步提示。
- 提供“生成第一篇 Wiki 页面”的最短路径。
- 让模型供应商配置错误更明确、更可操作。
- 保持默认本地入口 `http://127.0.0.1:8000`。

完成标准：

- 新用户可以 clone 项目、配置一个模型供应商、启动控制台并生成页面，而不需要先阅读架构文档。
- npm launcher 能清晰委托到 Python runtime，并在缺少本地 runtime 时给出可执行安装路径。

## 1.2.x：配置生命周期

目标：让配置稳定、可迁移、对用户数据安全。

重点：

- 引入明确的配置 schema version。
- 新增或强化 `knoar migrate`，用于配置和 vault 元数据迁移。
- 收紧配置校验和错误码。
- 密钥保留在 `.env`，不把真实 key 写入 `config.yaml`。
- 改善多知识库配置，但不增加默认单知识库流程的复杂度。
- UI 配置和 CLI 配置共享同一套校验契约。

完成标准：

- 跨版本配置变化有文档说明，也可以被机器检查。
- 用户遇到路径缺失、模型配置错误、旧配置文件时，可以通过诊断和迁移命令恢复。

## 1.3.x：资料来源生态

目标：扩展输入来源，同时保持 connector 边界清晰。

重点：

- 稳定 Markdown、Codex、Claude Code、Hermes、OpenClaw 和 generic chat connector。
- 在统一 `SourceDocument` 契约下支持更丰富的文件和网页来源。
- 文档预处理与资料摄入保持分离。
- 文件夹级和文件级输入选择保持一致。
- 长资料切分结果在报告中可见、可解释。
- 避免把来源专用逻辑写进语义 agent。

完成标准：

- 新增来源通常只需要新增 connector 和测试，不需要修改 ingest 核心。
- 用户可以看清楚每个来源生成了哪些页面、处理了哪些 segment。

## 1.4.x：机器索引层

目标：在不强依赖重型数据库的前提下提升检索。

重点：

- 引入独立于人类可读 `index.md` 的机器索引层。
- 优先使用 SQLite FTS/BM25 一类轻量本地索引。
- 向量检索作为可选增强，不作为默认安装依赖。
- 记录索引新鲜度、重建状态和失败状态。
- ingest、lint、query 共享一致的 index provider 契约。

完成标准：

- 中等规模 vault 的 query 质量提升，同时不要求用户部署向量基础设施。
- `index.md` 保持给人阅读，机器检索使用专用索引。

## 1.5.x：知识治理

目标：让自动维护更可信。

重点：

- lint 从确定性结构检查扩展到质量、重复、溯源、时效性治理。
- 保留基于风险和证据的 reviewed operation 模型。
- 为维护操作提供更清晰的前后 diff 报告。
- 跟踪未解决或反复被拒绝的维护问题。
- 完善事实性、完整性、清晰度、相关性、冗余度和来源支撑等质量指标。

完成标准：

- 安全修复可以自动执行。
- 复杂修复可以由维护 agent 审计后执行或延后，并给出证据。
- 用户能看清楚系统改了什么、为什么改。

## 1.6.x：控制台产品化

目标：让 UI 更像成熟产品，而不是开发控制台。

重点：

- 完善首次启动引导。
- 打磨资料来源、运行、报告、图谱、知识库、token 分析页面。
- 让运行报告直接可操作：展示写入页面、修改页面、diff 和跳转。
- 提升加载性能，避免页面跳转触发不必要扫描。
- 只有在能减少自定义 UI 复杂度时，才引入成熟组件系统。

完成标准：

- 用户可以通过控制台完成核心流程，而不需要理解每个内部报告字段。
- UI 能回答四个问题：配置了什么？正在运行什么？改了什么？下一步做什么？

## 1.7.x：CLI、API、Skill 闭环

目标：让所有用户入口保持一致。

重点：

- 保持公开 API 小而稳定：health、doctor、ingest、lint、query、runs、wiki pages。
- CLI 默认输出适合人读，`--json` 输出适合机器处理。
- Skill 聚焦宿主 AI 的上下文检索，不负责生成最终聊天回答。
- 只有能清晰映射到稳定 API 的能力，才进入 Skill。
- 保持 API response envelope 和 schema version。

完成标准：

- CLI、API、UI、Skill 像是同一系统的不同入口，而不是四套不同实现。
- 外部自动化可以依赖公开 API，而不需要追踪内部实现细节。

## 2.0.0：长期兼容基线

2.0.0 应该成为外部用户可以长期依赖的兼容基线。

2.0 需要冻结：

- 公开 API endpoint family 和 response envelope；
- 配置 schema 和迁移策略；
- vault 目录语义；
- connector 接口契约；
- source document schema；
- ingest、lint、query、runs 报告 schema；
- 基础包管理和 launcher 行为；
- 隐私与密钥处理规则。

## 2.0 前的非目标

这些能力有价值，但不应该阻塞 2.0：

- 多用户登录和权限；
- 托管 SaaS；
- 必选向量数据库；
- 内置大模型权重；
- 云同步；
- 协同编辑；
- 把 KnoArbor 做成通用聊天助手。

KnoArbor 应该继续保持为知识引擎，被其他工具调用，而不是变成另一个聊天入口。

## 指导原则

- 优先稳定契约，而不是盲目扩展功能。
- source connector 保持窄而可测试。
- 语义 agent 只处理需要语言理解的决策。
- 确定性校验不要交给模型。
- 不用宽泛兜底隐藏失败，而是输出可操作错误和报告。
- vault 是用户数据，测试和初始化都不能覆盖它。
- 每个生成或维护后的页面都必须能追溯到来源证据。
