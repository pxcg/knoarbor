# KnoArbor 桌面端体验审查

日期：2026-07-01

本文档用于功能主模块完成后的体验优化阶段。审查重点不是继续发现功能缺口，而是判断用户能否顺畅完成真实工作：配置模型、导入资料、浏览知识库、向知识库提问、查看证据和回看运行状态。

## 审查方法

本轮审查采用两种方式：

- 源码审查：重点查看前端路由、侧栏、会话、知识库、图谱、设置和运行页面的交互结构。
- 空白工作区走查：使用临时 vault 启动本地服务，模拟首次打开、无模型、无页面、无会话的桌面端状态。

本轮走查覆盖页面：

- 对话首页
- 流程页
- 知识库页
- 工作区设置
- 模型设置
- 无模型状态下的对话提交错误

## 总体判断

当前桌面端已经具备可用的主入口结构：侧栏收敛为“对话 / 流程 / 知识”，工作区设置统一承载配置，知识库和图谱也已经从功能上收窄到页面关系。这一方向是正确的。

主要体验问题不在“功能是否存在”，而在用户第一次进入时仍需要理解较多内部机制。产品现在还带有一些开发控制台气质：流程、报告、Token、阶段轨道、Source、运行记录等概念对研发调试很有用，但对普通桌面端用户并不是完成任务的第一语言。

下一阶段建议以三条主线优化：

1. 让首次使用路径更明确：没模型、没资料、没页面时直接告诉用户下一步。
2. 让核心工作流更短：从“导入资料”到“可以提问”的路径要显性化。
3. 让内部运行信息退到次级：保留诊断能力，但不要让它成为用户第一眼必须理解的内容。

## P0：首次使用缺少统一引导

### 现象

空白工作区首次进入默认打开“对话”。页面文案是“把零散资料编译成可追溯的 Wiki，再直接向你的知识库提问”，输入框也可输入内容。由于未配置模型，用户输入后点击发送才会看到错误：“当前模型不可用。请在设置中检查模型供应商后重试。”

这个错误提示本身是可行动的，有“打开设置”按钮；问题在于它出现得太晚。用户已经经历了一次失败请求。

### 影响

用户会把“没有完成必要配置”理解成“对话功能失败”。这会降低对桌面端稳定性的第一印象。

### 建议

在对话首页增加前置 readiness 状态，不等用户发送失败后才提示：

- 未配置聊天模型：在输入框上方显示“先配置模型”，提供“打开模型设置”主按钮。
- 知识库为空：提示“当前知识库还没有页面”，提供“导入资料”主按钮。
- 模型已配置但知识库为空：允许普通对话或明确说明“当前只能进行无知识库对话/请先导入资料”。
- 模型和知识库都就绪：显示正常欢迎文案。

实现上可以复用现有 `doctorReport`、`modelProviders`、`status.pages` 和 `openSettings()`，不需要新增复杂后端能力。

## P0：空知识库状态没有下一步动作

### 现象

知识库页空状态只显示“暂无页面”。右侧预览显示“选择一个页面，查看正文和链接上下文。”没有把用户导向“导入资料/知识编译”。

### 影响

用户进入知识页后会知道“没有内容”，但不知道“如何产生内容”。这尤其影响迁移 vault、新建知识库、首次安装后的体验。

### 建议

将知识库空状态改为任务型空状态：

- 标题：当前知识库还没有页面
- 说明：导入 Markdown、文档或会话后，KnoArbor 会生成可追溯页面。
- 主按钮：导入资料
- 次按钮：打开输入来源设置

图谱空状态也应类似，不只显示“没有页面可展示”，而是说明图谱来自页面之间的链接关系。

## P1：流程页信息密度偏高，仍像开发控制台

### 现象

点击侧栏“流程”后，二级导航包含：

- 运行
- 知识编译
- 校验维护
- 知识查询
- 运行报告
- Token 分析

默认页还显示阶段轨道：排队、输入、分段、标准化、原子、召回、规划、编译、评审、门禁、写入、完成。

### 影响

这对研发和高级用户有价值，但普通用户进入“流程”时可能无法判断自己应该点“知识编译”还是“知识查询”，也会被“原子、门禁、Token”等内部词汇打断。

### 建议

将“流程”重命名或重构为更任务化的入口：

- 一级入口可考虑叫“任务”或“处理”
- 默认展示“正在处理”和“最近任务”
- “知识编译”作为主操作入口
- “报告 / Token / 详细阶段”折叠到“详细信息”或“诊断视图”

保留运维能力，但降低默认可见度。

## P1：侧栏会话区和主对话空状态重复

### 现象

首次打开时，侧栏会话区显示“暂无对话”，主对话页也显示欢迎空状态。侧栏标题使用“知识库”，副标题又是“暂无对话”，概念上有轻微混淆。

### 影响

用户会同时看到两个空状态。侧栏到底是“知识库”还是“会话列表”不够直观。

### 建议

侧栏会话区建议明确命名为“会话”，并在无会话时只保留轻量提示：

- 标题：会话
- 空状态：暂无历史会话
- 新建按钮：使用明确图标和 tooltip

主对话页则负责 onboarding，不需要与侧栏重复解释“暂无对话”。

## P1：设置默认落点与用户阻塞原因不完全匹配

### 现象

点击“工作区设置”默认进入“知识库”分区。对一个无模型的新用户来说，当前真正阻塞对话的是“模型”分区。

### 影响

当用户从对话失败进入设置时，如果不能直接定位到模型分区，会增加寻找成本。

### 建议

支持带意图打开设置：

- `openSettings("models")`
- `openSettings("inputs")`
- `openSettings("diagnostics")`

对话页的“打开设置”应直接进入模型分区。知识库空状态的“导入资料”应直接进入知识编译或输入来源分区。

## P1：中英文和内部词汇仍有少量混用

### 现象

知识库页面的编辑和删除按钮仍显示 `Edit`、`Delete`、`Archive Page`、`Cancel`、`Save` 等英文。设置和流程中也仍有 `Token`、`YAML`、`Source` 这类技术词直接暴露。

### 影响

中英文混用会让产品成熟度显得不稳定。内部词汇会让普通用户觉得自己需要理解实现细节才能安全操作。

### 建议

分两类处理：

- 必须保留的技术名词：如 YAML、Token，可以加简短上下文，或放到高级设置/诊断区域。
- 普通操作词：全部走 i18n，不在 JSX 中硬编码英文。

重点文件：

- `web/src/pages/WikiPage.tsx`
- `web/src/i18n/data.ts`

## P2：顶部 GitHub 链接在桌面端主工作区中存在感偏高

### 现象

多个页面右上角固定显示 GitHub 链接。

### 影响

开源项目需要 GitHub 入口，但桌面端主工作区中，它不是用户完成知识库工作的核心操作。对于企业/联合开发场景，这个入口也可能产生品牌和产品归属感上的干扰。

### 建议

将 GitHub 入口放入关于/帮助/设置页，而不是每个主页面顶部固定显示。公开开源版本仍可保留，但降低主工作流干扰。

## P2：工作区设置内容完整，但仍偏配置表单

### 现象

设置页分区清晰，但整体仍是“配置项管理”。例如模型页有“供应商预设”“新增模型”，但首次用户还需要知道供应商、端点、环境变量等概念。

### 建议

模型配置可以增加一个轻量向导层：

- 选择供应商
- 填写 API Key 或选择本地模型
- 检查 API 连通性
- 保存并返回对话

高级字段继续保留在展开区，不进入默认路径。

## 建议的体验优化路线

### 第一轮：阻塞前置

目标：用户不再通过失败来理解系统状态。

建议任务：

- 对话页增加 readiness 面板。
- 无模型时发送按钮旁显示“配置模型”入口。
- 知识库空状态增加“导入资料”入口。
- 设置支持按分区打开。

### 第二轮：空状态任务化

目标：每个空状态都告诉用户下一步。

建议任务：

- 知识库空状态任务化。
- 图谱空状态任务化。
- 运行页无任务状态任务化。
- 侧栏历史会话空状态减重。

### 第三轮：降低控制台感

目标：普通用户默认只看到完成任务所需的信息。

建议任务：

- 流程页重命名和重排。
- 报告、Token、阶段轨道降级到详细/诊断视图。
- 顶部 GitHub 入口迁移到帮助/关于。
- 清理主界面内部术语。

### 第四轮：文案与 i18n 收口

目标：界面语言稳定、客观、统一。

建议任务：

- 移除页面 JSX 中硬编码英文按钮。
- 统一“知识库 / 页面 / 资料 / 会话 / 任务 / 运行”的中文词表。
- 为危险动作统一使用“归档”而不是“删除”。

## 验收标准

体验优化完成后，建议用以下场景验收：

1. 新用户打开空白桌面端，能在 1 分钟内知道需要配置模型和导入资料。
2. 空知识库状态下，用户不需要猜测入口即可进入导入资料流程。
3. 模型未配置时，对话页不会让用户先失败一次才知道原因。
4. 迁移 vault 后，如果没有页面或附件，界面提示能指出缺什么，而不是只显示空白。
5. 普通用户完成“导入资料 -> 查看页面 -> 提问 -> 查看证据”的路径时，不需要理解 source digest、ledger、run stage、token ledger 等内部概念。
